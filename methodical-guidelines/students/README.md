# Методические указания обучающимся

Указания определяют порядок выполнения, сдачи и защиты контрольно-измерительных материалов дисциплины, правила использования генеративного искусственного интеллекта и порядок разрешения спорных ситуаций.

## 1. Общий порядок работы

Все задания выполняются в личном или командном репозитории, выдаваемом через GitHub Classroom. Артефакты (документы, диаграммы, код проверок) ведутся в текстовом формате под контролем версий. Сдача выполняется через pull request; к проверке принимаются работы, прошедшие автоматическую формальную проверку.

Порядок выполнения любого задания:

1. получить шаблон репозитория по ссылке-приглашению;
2. изучить контрольно-измерительный материал целиком, включая критерии оценивания и ориентиры для проверяющего — они показывают, чем полный ответ отличается от формального;
3. выполнить задание, фиксируя промежуточные результаты отдельными коммитами;
4. запустить локальную проверку (для КИМ-2.5 — `python attachments/ci-check.py .`);
5. заполнить декларацию использования генеративного искусственного интеллекта;
6. открыть pull request до истечения срока;
7. пройти защиту.

## 2. Работа с репозиторием

**Коммиты.** Один коммит — одно логически завершённое изменение с понятным сообщением. Оформление всей работы единственным коммитом не является нарушением, но служит основанием для расширенного опроса на защите: история изменений показывает процесс работы и используется при проверке.

**Именование файлов** соответствует структуре, приведённой в разделе «Формат сдачи» каждого КИМ. Отклонение от структуры приводит к отрицательному результату автоматической проверки.

**Внутреннее рецензирование** (в командной работе): каждый артефакт рецензируется участником другой роли. Автор и рецензент фиксируются в pull request.

## 3. Использование генеративного искусственного интеллекта

Использование генеративных моделей при выполнении заданий **разрешено** и является **обязательным предметом декларирования**. Оценивается не факт использования, а качество контроля над результатом.

**Разрешается:** подготовка черновиков, критика собственных решений, разбор документации, подбор источников, написание вспомогательного кода.

**Не допускается:** сдача сгенерированного текста без проверки; вынесение итоговых решений (вердиктов, выводов о целесообразности, решений о вводе в эксплуатацию) средствами модели; использование генеративных моделей во время экзамена.

**Обязательно:**

- каждое задание сопровождается декларацией использования ИИ;
- каждое числовое утверждение и каждая ссылка на стандарт проверяются по первоисточнику;
- непроверенные утверждения явно обозначаются как непроверенные;
- числовые результаты приводятся только из собственного прогона или расчёта.

Ссылка на несуществующий или неверно названный стандарт, а также приведение числового результата, отсутствующего в материалах работы, снижают оценку. Приведение результата, который невозможно воспроизвести по представленным материалам, является основанием для непринятия работы.

### 3.1. Форма декларации

Декларация приводится в файле `README.md` сдаваемой работы.

```markdown
## Декларация использования ИИ

| Инструмент и модель | Что выполнялось | Что проверено и как | Что исправлено |
|---|---|---|---|
| <модель> | <задача> | <способ проверки> | <внесённые изменения> |

**Не проверено (остаточный риск):** <перечень непроверенных утверждений и последствия при их недостоверности>
```

Раздел «Не проверено» обязателен. Честное указание границы проверенного оценивается положительно: способность очертить область неопределённости является проверяемым результатом обучения.

### 3.2. Рекомендуемый порядок применения

Приём, повышающий качество работы: сначала разработать решение самостоятельно, затем прогнать его через промпт-критик (см. [банк промптов](../../resources/llm-prompts/README.md)) и принять решение по каждому замечанию. В декларации указываются замечания, с которыми вы **не согласились**, и обоснование несогласия — обоснованное несогласие оценивается выше согласия.

## 4. Подготовка к защите

Защита проверяет понимание представленных решений, а не их оформление. Вопросы задаются по конкретным фрагментам работы, истории изменений и декларации использования ИИ. Банк вопросов для защиты проектной работы открыт: [`Project/attachments/defense-questions.md`](../../Project/attachments/defense-questions.md).

Подготовка к защите:

- по каждому числовому значению в работе восстановите, откуда оно взято и что произойдёт при его изменении;
- по каждому принятому решению сформулируйте отвергнутую альтернативу и цену выбора;
- перечитайте собственные коммиты: вопросы задаются по конкретным изменениям;
- будьте готовы к изменению вводных, выдаваемому на защите без подготовки.

Работа, которую обучающийся не может обосновать на защите, не засчитывается независимо от формального качества артефактов.

## 5. Типовые ошибки

| Ошибка | Последствие | Как избежать |
|---|---|---|
| Требование без критерия приёмки | требование неверифицируемо, снижение по критерию измеримости | для каждого требования указывать способ проверки |
| Метрика без baseline и условий замера | требование к качеству модели невозможно проверить | указывать метрику, значение, базовое решение, условия и разрезы |
| Числовой порог без обоснования | значение выглядит произвольным | обосновывать порог через бизнес-цель или отраслевую практику |
| Только агрегированная метрика | скрывает деградацию по подгруппам | приводить метрику в разрезах |
| Элемент архитектуры без связи с требованием | нарушение трассируемости | удалять либо оформлять запрос на изменение спецификации |
| Формальные альтернативы в ADR | решение признаётся непроработанным | указывать негативные последствия и цену выбранного варианта |
| Ссылка на устаревшую редакцию стандарта | дефект оформления, снятие баллов | сверять редакцию по [перечню стандартов](../../resources/other/README.md) |
| Декларация ИИ без раздела «Не проверено» | работа возвращается без оценки | указывать границу проверенного |
| Сдача одним коммитом в последний день | расширенный опрос на защите | фиксировать промежуточные результаты |

## 6. Сроки и порядок пересдачи

Сроки устанавливаются календарным планом дисциплины. Нарушение срока без уважительной причины снижает балл оценочного средства на 10 % за каждую неделю просрочки (см. [систему оценивания](../../docs/grading.md), раздел 5).

Работа, оценённая ниже 60 баллов, дорабатывается и представляется повторно в срок, согласованный с преподавателем. Порядок ликвидации задолженностей и пересдачи экзамена определяется локальными нормативными актами образовательной организации.

## 7. Порядок разрешения спорных ситуаций

Несогласие с оценкой излагается письменно с указанием критерия оценивания и обоснованием. Разбор проводится по представленным материалам работы: критерии и ориентиры для проверяющего опубликованы в каждом КИМ, что позволяет соотнести оценку с формальным основанием.

Расхождение между взаимооценкой участников команды и оценкой преподавателя разбирается индивидуально на защите (см. [проектную работу](../../Project/README.md), раздел 9).
